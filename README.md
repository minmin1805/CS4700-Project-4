# CS4700-Project-4


## My High-level approach
-When the program runs, the main() function in both files (4700send.js and 4700recv.js) will be triggered first.
-In 4700send.js, it waits for data from stdin. Once data is available, appendDataHelper creates chunks of data with a size of 1400 bytes. When this chunk is full (1400 bytes), it is sent to the receiver and the packet is stored in a notAckMap (this stores packets that have been sent and are waiting to be acked).
-When the sender receives the ack from the receiver, it processes it in the fromReceiverHandler() function. Specifically, the sender recalculates the checksum and compares it to the receiver's checksum. Then it removes this packet from notAckMap() and, since the packet has been acked, adds it to the successDataSoFar array. Lastly, based on the receivedNeededSN from the ack, the sender will also process packets with sequence numbers before this receivedNeededSN to mark them as successfully acked.
- For 4700recv.js, it waits for packets from the sender. Once received, it processes this packet with the processDatagram() function. Then, it must calculate the checksum again and compare to see if the data was lost or corrupted during transmission. After that, if the sequence number sent from the sender is greater than the sequence number it is waiting for, it will save the packet to receivedEarlyMap (data that arrived too early). If the data is duplicated, it will ack to notify the sender. If the received sequence number matches the one it is already waiting for, it will ack, increment the waiting sequence number by 1, and check with checkForEarlyData() to see if it can print the earlier arriving data. There are other helper functions and extra features like expanding window size and adjusting the RTO, but excluding those, the steps above are the basic way my TCP works.

## Challenges that I had
-One of the difficulties I encountered was choosing a data model to represent the format and size of each packet. Previously, I implemented it using Buffer and had to allocate data, but I found it quite complicated. I had to allocate data for each field in a packet, and this step took a lot of time. However, after carefully checking the run file, I found that the data sent by stdin is in string format, so I thought the information for each packet could be represented as a string, and the packet itself could be represented as a JSON object. After trying this approach, everything became easier to understand, more intuitive, and the implementation was less complicated. I spent a lot of time on this step; I should have thought carefully and planned to choose the ideal format for a packet initially.

-A further difficulty was with the checksum method. I chose the wrong approach at first (I initially chose to convert each character to ASCII and sum them up, then did the same for the receiver side, but this didn't solve the problem when the data was corrupted in many places). I spent a considerable amount of time experimenting with several methods and found that before summing them up, I could take the ASCII value of each character and multiply it by 3 first.

## List of properties/features of my design
- Congestion control: For level 7, I used the knowledge from the lecture slides on congestion control to adjust the window size. I really liked this feature because I got to see firsthand how the knowledge I learned in class was transformed into a concrete feature in the project.
- RTO adjustment: For level 6, I once again used the math calculations I learned in the TCP/UDP lecture slides to calculate the new RTT and from there calculate the updated RTO.
- Don't print duplicate packets for receiver: I made it so the receiver could only ack the duplicate packet back to the sender and not print it out again.
- Checksum: I used checksums to check for corrupted data for both the sender and receiver. I converted each character to an ASCII value, multiplied it by 3, and then added them together.
- Receiver can handle out-of-order packets: I implemented a map on the receiver side so that whenever a packet with a sequence number greater than the sequence number it's waiting for arrives, it is saved. These packets will then be pulled out for processing and printing each time a gap between the sequence numbers is filled.
